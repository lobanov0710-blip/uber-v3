# OWNER/Superadmin: проверка Transfer Admin на телефоне

Объём подтверждён владельцем 2026-11-15: только Admin/OWNER на STAGING,
приватные действия на его Windows PowerShell. Driver G1 остаётся на паузе.
Это отдельная подготовка, не прохождение полного D3 gate и не production release.

## Что приготовлено

- APK Admin с STAGING endpoint, отдельным package/signing от Driver. Передаваемый
  debug APK предназначен только для этой проверки; release/upload key ещё не создан.
- Защищённый локальный CLI, закреплённый за Worker `uber-v3-staging`,
  `uber-v3-staging.lobanov0710.workers.dev`, D1 `transfer-servis52-staging`
  (`66474481-a123-47f9-81b4-12af7565ec8d`) и утверждённым staging KV.
- Режим `ADMIN_PHONE_TEST_ONLY=true`: только OWNER с MFA. Driver/public/legacy API,
  private file endpoints и фоновые Driver/support jobs закрыты. Существующие
  регистрации скрыты. Первая проверка — вход, MFA, пустая очередь, refresh/logout.
  CLI не создаёт фиктивных регистраций и не загружает документы.
- Никаких публичных provisioning/reset endpoint. Существующий OWNER/его пароль
  не заменяются. При существующем TOTP подключении CLI не сбрасывает фактор.

R2 и Firebase здесь не подключаются. Их отсутствие не обходится для Driver:
полный D3 preflight остаётся без изменений, G1 приостановлен.

## Первый этап: только чтение и локальные файлы

Скачайте проверенный ZIP настройки и распакуйте в отдельную папку на своём ПК.
Не используйте рабочую production-папку. Сверьте SHA256 ZIP с выданным SHA256SUMS:

```powershell
Get-FileHash .\owner-phone-setup.zip -Algorithm SHA256
Expand-Archive .\owner-phone-setup.zip -DestinationPath .\owner-phone-setup
Set-Location .\owner-phone-setup
node --version
npm --version
npm ci --ignore-scripts
node .\scripts\adminOwnerPhoneSetup.mjs init
node .\node_modules\wrangler\bin\wrangler.js login
node .\scripts\adminOwnerPhoneSetup.mjs plan
```

Используйте Node.js 24 LTS и npm 11.9.0 (зафиксированные зависимости в lockfile).
Если установлен другой npm: `npm install --global npm@11.9.0 --ignore-scripts`.
`init` спросит Cloudflare Account ID — публичный идентификатор из Dashboard,
32 шестнадцатеричных символа, не API-токен. Cloudflare `login` откроет браузер;
вход и выдачу прав выполняете сами. Токены/коды браузерного входа в чат не нужны.
Если права или target отличаются, остановитесь и сообщите только название шага.

CLI требует обычный приватный интерактивный PowerShell, не CI, не transcript,
не запись экрана и не перенаправление вывода. Пароли/ключи не передаются аргументами.
Windows-папка должна быть доступна только вашей учётной записи.

`plan` читает состояние конкретного STAGING Worker/БД/список имён secrets и делает
локальный bundle dry-run. Он не выполняет remote migrations/deploy, не создаёт
OWNER и не меняет secrets. CLI сверяет source manifest, точные DB/KV bindings,
18-файловую цепочку миграций и отсутствие неожиданных bindings.
Поддерживается только pending `0018_owner_totp_mfa.sql`; другие расхождения
требуют разбора, автоматического обхода нет.

Пришлите **только** `.owner-phone\admin-phone-plan.public.json`. В нём нет
паролей, токенов, login/ID OWNER, seed или bootstrap-кода. Другие файлы из
`.owner-phone`, локальный config и вывод Cloudflare присылать не нужно.
**До разбора отчёта и явного утверждения remote изменений следующие команды
не выполнять.** Это контроль фактического STAGING, а не повторная настройка G1.

## После разбора плана и отдельного утверждения

Каждый изменяющий шаг требует точной фразы в приватном терминале:

```powershell
node .\scripts\adminOwnerPhoneSetup.mjs schema
node .\scripts\adminOwnerPhoneSetup.mjs isolate
node .\scripts\adminOwnerPhoneSetup.mjs jwt-key
node .\scripts\adminOwnerPhoneSetup.mjs mfa-key
node .\scripts\adminOwnerPhoneSetup.mjs plan
node .\scripts\adminOwnerPhoneSetup.mjs owner
```

`schema`: только подтверждённая pending 0018, повторно не применяется.
`isolate`: до создания ключей развернуть OWNER-only Worker с закрытыми Driver/
public/legacy/private-file API. Допустимо только для подтверждённого первого
запуска: OWNER отсутствует, factors 0, оба ключа отсутствуют, 0018 применена.
Фраза: `ISOLATE uber-v3-staging OWNER ONLY`. CLI проверяет header и закрытые
маршруты. Без ключей и OWNER вход остаётся недоступным.
`secret put` меняет действующий Worker, поэтому сначала изоляция, затем ключи.
Оба шага создания ключей повторно проверяют route isolation перед записью.
`jwt-key`: отдельный CSPRNG 32 bytes → base64 → Wrangler stdin для JWT_SECRET;
существующий secret не заменяется. Никаких значений в выводе/argv/файлах.
`mfa-key`: другой независимый CSPRNG 32 bytes → Wrangler stdin, ни ключа в аргументах/файлах/выводе,
ни автоматической ротации. Существующий ключ сохраняется; факторы без исходного
ключа требуют отдельного восстановления, CLI их не сбрасывает.
`deploy` остаётся отдельным действием для повторного развёртывания с уже готовыми
ключами; в первом запуске выше его заменяет `isolate`. Только фиксированный STAGING, проверка закрытых Driver routes и
`X-Transfer-Test-Scope: owner_phone`. Если после jwt-key JWT_SECRET всё ещё отсутствует или есть
неожиданные bindings, остановка для отдельного разбора; production не затрагивается.

`owner`: если OWNER существует без TOTP — использует его; если binding отсутствует,
владелец сам выбирает новую учётную запись или точный существующий active admin.
Новый пароль вводится скрыто дважды, 16–128 символов. Только password verifier
попадает в SQL. Bind/account/bootstrap/revocation/audit применяются атомарным D1
file import с rollback; временный файл содержит только verifier/digest и удаляется.
Bootstrap TTL 15 минут, считается по часам БД, максимум 3 ошибки; код показывается
только в приватном терминале после проверки записи. Секреты в журнал не включаются.
После timeout/сбоя не повторяйте запись вслепую: сначала новый read-only `plan`.

## На телефоне

1. Установите выданный debug APK Transfer Admin (Android 8+). Используйте только
   тестовые данные и STAGING пароль; это ещё не production-приложение.
2. Введите приватные OWNER login/password, затем одноразовый bootstrap из терминала.
3. Admin покажет Base32-ключ TOTP. Для настройки на том же телефоне перепишите
   его приватно на бумагу, затем добавьте вручную в аутентификатор:
   TOTP, SHA-1, 6 цифр, 30 секунд. Не отправляйте ключ в чат, не используйте общий
   буфер обмена. После безопасного сохранения удалите временную запись.
4. Вернитесь в Admin в пределах исходных 5 минут, введите TOTP и подтвердите.
   При переходе в аутентификатор ключ и поля ввода очищаются; ID попытки/настройки
   остаются только в RAM. Повторный переход не продлевает срок. При перезапуске
   процесса или истечении срока требуется новый вход/подключение.
5. Сразу сохраните десять recovery-кодов в личном менеджере паролей/другом приватном
   месте, прежде чем сворачивать Admin: коды выдаются один раз и очищаются в фоне.
6. Подтверждение подключения не выдаёт рабочую сессию. Выполните новый вход паролем
   и новым TOTP (дождитесь следующего 30-секундного кода после enrollment).
7. Проверьте роль владельца, пометку STAGING, пустую очередь и выход. При новом входе
   переключитесь в аутентификатор и вернитесь: ID сохраняется, введённые коды — нет.

При уходе в фон во время незавершённого сетевого запроса клиент отменяет его и
не принимает запоздалую сессию. Сервер мог уже обработать запрос: не повторяйте
одноразовое подтверждение вслепую; сначала проверьте фактическое состояние через
новый вход/план. Автоматического снятия MFA, password reset или SMS-обхода нет.

## Границы подтверждения

Локальные тесты и CI не подтверждают ваш Cloudflare account, текущее live-состояние
STAGING или прохождение на вашем телефоне. Это станет проверяемым только после
приватного `plan`, утверждённых remote шагов и ручной проверки. В журнал передаются
только action/result, время и безопасный отчёт, без реквизитов входа.

## Повторный init при существующем config

Если init остановился после Account ID, проверьте только наличие файла:
`Test-Path .\wrangler.admin-phone.staging.json`. При True повторное создание
config не требуется: init использует flag=wx и защищает существующий файл от
перезаписи. Ничего не удаляйте и не отключайте checks. Выполните:

```powershell
node .\scripts\adminOwnerPhoneSetup.mjs plan
```

Plan проверяет существующий config и состояние STAGING без remote writes.
После его успешного завершения продолжайте утверждённую последовательность с
schema. При ошибке plan остановитесь и сообщите action name, без содержимого
private config/credentials. При False причина может быть в формате public
Account ID или доступе на запись; требуется уточнение, не автоматический обход.


## Ошибка owner сразу после выбора n

Первоначальный пакет принимает только заглавные N/E. Если введена строчная n
и ошибка произошла до следующего запроса/PROVISION, повторите:

```powershell
node .\scripts\adminOwnerPhoneSetup.mjs owner
```

Введите один символ `N` латиницей без кавычек. Этот ранний отказ не отправляет
provisioning SQL, поэтому повтор не создаёт дубликат. Обновлённый CLI принимает
оба регистра n/N/e/E; роль по-прежнему выбирает владелец, default не добавлен.
Текущим пакетом можно продолжать с заглавной N, без новой установки/перепаковки
и без ручного редактирования защищённых manifest hashes. При ошибке после
PROVISION повторять запись вслепую нельзя — сначала read-only plan.
