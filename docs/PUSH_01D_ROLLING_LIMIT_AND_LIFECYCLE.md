# PUSH-01D — скользящий лимит выдачи и безопасный срок жизни FCM-токенов

**Дата:** 03.11.2026. **Статус:** отдельная feature-ветка поверх [PUSH-01C PR №15](https://github.com/lobanov0710-blip/uber-v3/pull/15). Не применять миграции и не включать public endpoints без отдельного согласия.  
**Контракт:** frozen API v1 не изменяется; staff push и текущие заказы не меняются.

## Что исправлено

1. **Настоящее скользящее окно 60 секунд.** Существующая таблица `passenger_push_grant_limits` из 0006 реализовывала фиксированное окно от первого события. В миграции `0007_passenger_push_grant_events.sql` вводится аддитивный журнал попыток успешной выдачи — `event_id`, `order_id`, `created_at`. Одной атомарной SQL-командой `INSERT ... SELECT WHERE COUNT(last 60s) < 5` выдача разрешается не более пяти раз за последние 60 секунд. События отказов не сохраняются в эту таблицу.
2. **Изолированное обслуживание срока жизни.** Модуль `passengerPushLifecycle.js` без HTTP, Cron и FCM. Предварительная проверка `previewPassengerPushMaintenance` возвращает только количество записей; `maintainPassengerPushData` при *явном авторизованном вызове*:
   - заменяет FCM-токены зарегистрированных устройств с `revoked_at != NULL`, `expires_at <= now` или завершённым/отменённым заказом на служебное значение `__REDACTED__`;
   - сохраняет `installation_id`, `order_id`, `revoked_at` как tombstone, предотвращающий повторную регистрацию до утверждения политики перевязки;
   - удаляет **события выдачи старше 5 минут** (при лимите 60 секунд) и **использованные jti старше 1 часа** (при максимальном grant TTL 300 секунд с запасом на рассинхронизацию);
   - не пишет в `orders`, `quotes`, `staff_*`; не обращается к Firebase и не отправляет пуши.
3. **Защита служебной метки.** `__REDACTED__` не может быть принята как новый FCM-токен через сервис или транзакционный слой.
4. **Тесты SQLite/Node.** Тесты применения миграций 0001–0007, SQL-лимита на границе окна, отката повторного `jti`, редактирования истёкших/отозванных/терминальных токенов, сохранения действующего токена и целостности staff таблиц.

## Границы безопасности

- В `router.js` не добавлен публичный endpoint обслуживания. **Нет** расписания Cron или включённого Worker; до отдельного одобрения данные production не изменяются.
- Сначала утвердить retention и способ безопасного перевыпуска `installationId`, чтобы tombstone не создавал необратимый UX-блок для легального пассажира.
- До реального включения необходим **WAF/rate limit на публичном PHP-шлюзе до выпуска HMAC**, поскольку текущий D1 лимитер защищает лишь подтверждённый `orderId` и не ограничивает неавторизованные обращения/разные заказы по IP. Конкретное правило и пороги должны быть согласованы отдельно, без применения к существующему заказу/калькулятору и водительским запросам.
- Важное ограничение: пока maintenance не вызывается по безопасному расписанию, FCM-токены **не очищаются автоматически**. Нельзя заявлять выполнение GDPR/retention, пока это не реализовано и не проверено. Превью само ничего не удаляет.
- Срок регистрации в PUSH-01A — предварительно 7 дней. Для этого PR не назначен пользовательский SLA и нет cleanup с удалением tombstones (такая операция должна отдельно рассмотреть privacy и abuse).
- Старые миграции `0005`, `0006` не править (схемы могли применяться вне теста), таблица `passenger_push_grant_limits` остаётся, но больше не используется кодом, её удаление вынести в отдельную безопасную миграцию после развёртывания/анализа.
- Нельзя применять `0007` отдельно: её использует код поверх ещё не объединённых/неприменённых `0005` и `0006`.
