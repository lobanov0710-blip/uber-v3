# G2: хранилище доверенной проверки автомобиля

Основание: утверждённый Admin classification contract, запрет новых прав диспетчерам, привязка версии при первом сохранении и обязательный цвет. Ветка arch/g2-trusted-vehicle-assessment от проверенного PR39. Это внутренний storage prerequisite перед публичным review POST и admission orchestration, не их завершение.

## Реализовано

Migration0023 добавляет immutable vehicle_trusted_assessments, immutable vehicle_assessment_invalidations и представление vehicle_current_trusted_assessments. История содержит точные фактические параметры, привязку input revision и pinned rule, отдельную basis rule для исключения, решения условий, ID/revision СТС, серверные actor/time, основание и минимальный audit reference. Класс кандидата хранится отдельно от vehicles.class. Нет seed, backfill, перезаписи старых0019 snapshots или назначения версии legacy.

Server-internal recordTrustedVehicleAssessment проверяет actual staff/session/tokenVersion/grants и существующее OWNER MFA в SQL, а не входные flags. Обычное подтверждение использует vehicles.verify; исключение только OWNER/vehicles.approve_exception (OWNER уже имеет vehicles.verify через существующее *). Диспетчер не получает новых прав. Основание и обе стороны verified СТС конкретного владельца/машины, точные revisions обязательны; документ другого авто/водителя, другого типа, pending/rejected или истёкший не подтверждает параметры. Чтение содержимого документов не предоставляется.

Новая immutable assessment, CAS общей vehicle revision, claim/replay receipt и audit записываются одной D1 batch. Внутренний storage поднимает только техническую revision/updated_at для CAS, не изменяет make/model/year, powertrain, vehicles.class/status или линию/заказ. Это позволяет отдельно проверить историю до открытия опасной проекции. Мутация возвращает только assessment ID/revisions/системный результат; основание и evidence отсутствуют в replay receipt. Неизвестные поля, класс, год/powertrain verified flags, actor/role отвергаются. Повтор проверяет текущий доступ. Неизвестный ACK не запускает автоматический replay.

Общий проверенный SQL authorizer выделен из rule service в adminClassifierAccess без изменения политики; прежние rule API проходят20 regressions. Pure decision слой получает только авторитетную версию из БД: unknown model/малый год/неполные или unmet условия дают manual_review; class берётся из rule. Пропуск условия не равен подтверждению; неизвестные/дублированные IDs отвергаются. OWNER может явно подтвердить допустимые year/condition waivers по модели той же марки, сохраняя фактическую модель. BEV исключён даже при exception; Comfort только sedan/crossover, Business sedan кроме Li Auto L7/L9 crossover. Minivan сохраняет определение своей строки. SQL независимо запрещает forged candidate с BEV/неправильным кузовом/годом/неподтверждёнными условиями/чужой маркой/неверным audit.

При смене make/model/year/powertrain/VIN/номера/владельца или материала/статуса/revision/типа/связи/срока selected evidence immutable invalidation отменяет доверие. Удаление selected документа тоже отменяет его. Возврат прежних значений не оживляет старый результат; требуется новое подтверждение. Цвет и unrelated revisions, публикация нового rule head не отменяют привязку/старую проверку. Новая assessment любого outcome заменяет прежнюю current; старый candidate не всплывает после excluded/manual_review. История не удаляется/не переписывается. Истечение срока evidence проверяется также при чтении view.

## Границы этапа

Публичный POST classification/review остаётся404, classification GET пока сохраняет прежнюю публичную проекцию без trusted history. Новый внутренний результат не активирован для допуска. Коррекция make/model/year в этой функции возвращает vehicle_parameter_correction_required; legacy без binding требует отдельно запланированный inventory, фиктивной версии нет. Это явные незавершённые части публичной orchestration, не новые бизнес-запреты владельца.

Следующий подэтап утверждённого контракта: атомарные исправления параметров и safe stop/manual dispatcher handoff, проекция/история/evidence в GET и публичный review POST, единый guard для старого approve и всех line/assign/reassign/phase/done SQL paths; затем Admin UI/DTO. Здесь не включены окончательное одобрение, identity provider, реальные документы/загрузка, новый APK или OWNER-phone allowlist. Полный powertrain обзор121 строк/legacy/seed activation также pending. G1paused,D4–D7pending. Нет remote migration, merge или deploy.

## Проверка

15 новых actual SQLite/auth сценариев (включая parallel CAS/replay, настоящую OWNER MFA через synthetic login, matching evidence, exceptions, permanent invalidations и rollback),20 existing rule,17 binding,4 MFA transport PASS локально. Offline migrations23,preflight12,reference6 PASS. Проверена совместимость trigger-inclusive D1 metadata: Driver vehicle mutation уже использует top-level SQL changes(); существующая модерация документов меняет только pending и не создаёт новую invalidation действующего verified evidence (оно уже инвалидировано переходом в pending). Чтение приватной provider metadata не требуется. Full backend CI и отдельный native D1 migration/storage workflow обязательны и пока pending. SQLite требует integrity_check, native D1 — документированные quick_check/FK. CI inventory/точные SHA/hashes будут в receipt после выполнения; Android runtime не менялся.
