# Проверка автомобиля и управление правилами: проект контракта

**Статус: предложено, не утверждено и не реализовано.** Основание — решения
владельца о системном классе, проверке года/исполнения, исключениях и версиях.
Этот документ не разрешает merge, deploy, seed или расширение OWNER-only STAGING.
Машиночитаемая форма: [OpenAPI](admin-vehicle-classification-v1.proposed.openapi.json).
Результаты сверки кода: [аудит](ADMIN_VEHICLE_CLASSIFICATION_AUDIT_2026-11-17.json).

## Что предлагается утвердить

1. Проверка параметров конкретного автомобиля — существующее `vehicles.verify`.
   Изменение общего справочника — отдельное `vehicle_rules.manage`; допуск
   конкретного исключения — отдельное `vehicles.approve_exception` вместе с
   `vehicles.verify`. Диспетчеру эти новые права автоматически не выдаются.
   OWNER использует существующее `*` и действующее серверное MFA; отдельного
   нового способа входа или роли не вводится. Чтение правил — `vehicles.read`.
2. Версия правила закрепляется **при первом сохранении автомобиля**. Пока год
   и исполнение не проверены, эта привязка не даёт класс или допуск. Смена
   марки/модели/года создаёт новую привязку к текущей версии, как уже решил
   владелец. Изменение цвета, фото, статуса, служебной revision или повтор
   запроса сохраняет прежнюю привязку. Это уточнение момента фиксации версии,
   ранее отдельно не выбранного владельцем; до утверждения не применять.
3. Администратор явно подтверждает параметры по документам и условия правила.
   Он может исправить параметры с историей, выбрать соответствующую модель
   той же марки для исключения либо создать модель/новую версию правила при
   наличии отдельного права. Класс конкретного автомобиля вычисляет сервер.
   Полностью электрический автомобиль и запрещённый бизнес-кузов не допускаются
   исключением; Li Auto L7/L9 сохраняют уже утверждённое отдельное разрешение.

Предлагаемое разделение прав и момент фиксации версии требуют ответа владельца.
Остальные пункты конкретизируют ранее утверждённые требования; ответы о том,
кто назначает замену, допуске без года, тарифах и сроке применения правил
повторно не запрашиваются.

## Действующие бизнес-границы

Класс не поступает от Driver или из формы решения по автомобилю. Для
неизвестной модели, года ниже порога и непроверенных условий — ручная проверка,
а не автоматический отказ или допуск. Исправление устранимого условия и
рассмотрение исключения сохраняются. Базовая модель сопоставления должна
принадлежать той же подтверждённой марке: межмарочная подмена не утверждена.
Неизвестную марку не добавлять автоматически к утверждённому составу142 марок.

Комфорт: седан/кроссовер. Бизнес: седан; кроссоверы Li Auto L7/L9 — конкретные
исключения владельца. Для Минивэна сохраняются условия его утверждённой строки;
новое ограничение кузова не вводится. Гибрид не исключается по одному названию
модели, версия проверяется по документам. BEV не может получить класс даже
при наличии права исключений или авторства общего правила.

Исходные годы и примечания121 оставшихся строк сохраняются при подготовке
первого набора. Порог2023 применяется там, где он утверждён, а не ко всему
историческому списку. Полный обзор силовых исполнений ещё не завершён; этот
контракт не объявляет оставшийся список проверенным и не включает его в runtime.

## Предлагаемые операции

| Операция | Право / назначение |
|---|---|
| GET /v1/admin/vehicle-rules | vehicles.read; явный поиск по марке/модели, limit1..50, scoped opaque cursor, без списка водительских записей |
| GET /v1/admin/vehicle-rules/versions/{version} | vehicles.read; точная неизменяемая версия и её условия |
| POST /v1/admin/vehicle-rules | vehicle_rules.manage; новая модель/версия с CAS expectedCurrentVersion, обязательным основанием и атомарным аудитом |
| GET /v1/admin/vehicles/{vehicleId}/classification | vehicles.verify; собственные параметры автомобиля в рамках административной карточки, привязка версии, проверки и предыдущие результаты |
| POST /v1/admin/vehicles/{vehicleId}/classification/review | vehicles.verify; проверка/исправление параметров, новый результат классификации. mode=exception дополнительно требует vehicles.approve_exception |

Существующий POST review/items/vehicle/{id} остаётся отдельным итоговым
одобрением автомобиля. Он обязан в SQL проверить актуальное подтверждение
параметров, допустимый системный результат, документы и фото. Новая операция
классификации **не выставляет approved**, не одобряет identity и не включает
линию. Старый Admin-клиент не может обойти guard обычной кнопкой одобрения.

## Проверка параметров конкретного автомобиля

POST review принимает expectedRevision, expectedInputRevision,
expectedRuleVersion, mode, parameters, evidence, conditions, exception, reason.
Поля vehicleClass, approved, yearVerified, powertrainVerified, role, permissions
и client-supplied actor запрещены. parameters: make, model, modelYear,
powertrain (`combustion|hybrid|battery_electric`), bodyType
(`sedan|crossover|minivan|other`). Год — целое число1..9999 как формат, а допуск
по году задаётся выбранным правилом. Неизвестный/непроверенный параметр не
превращается в успешное подтверждение по умолчанию.

evidence содержит только ID и revision СТС конкретного автомобиля/водителя.
Сервер проверяет принадлежность, тип, verified status, неизменность версии и
право доступа к материалам. Подтверждение проверки года/исполнения записывается
с серверными actor/time и привязкой к параметрам, а не берётся из Driver-флага.
Чтение содержимого СТС сохраняет существующие отдельные sensitive permissions;
эта операция их не выдаёт. Новый UI не открывает материалы без этих прав.
До D5/G1 используются только synthetic документы и offline/native fixtures.

conditions перечисляет ID условий точной версии и явный результат
`satisfied|unmet` по каждому. Неизвестные/дублированные ID отклоняются;
пропущенное условие остаётся непроверенным, а не удовлетворённым. Автоматически
разбирать свободный notes или угадывать поколение, кузов, салон нельзя.
Исходные примечания сохраняются дословно; серверные condition IDs создаются
при создании неизменяемой версии. Возврат на исправление содержит основание.

Обычная проверка использует закреплённую версию той же модели. При фактической
коррекции make/model/modelYear администратором параметры автомобиля меняются
явно, исходные значения сохраняются в истории, ревизия растёт, класс/допуск
сбрасываются и берётся текущая версия. Действует уже утверждённая безопасная
остановка/ручное действие диспетчера при активном назначении. Исправление
силовой установки, кузова или смена доказательств также инвалидирует доверие
к старому результату; без смены make/model/year версия правила сохраняется.

Для исключения exception содержит basisRuleVersion, yearBelowMinimum и
waivedConditionIds. ID версии указывает соответствующую модель из справочника;
его класс сервер читает сам. Реальная модель автомобиля не заменяется моделью
сопоставления. Основание обязательно. Можно явно рассмотреть неподходящий год
или перечисленные неисполненные условия; запрещённые BEV/кузов этим не
обходятся. Новая модель сначала создаётся отдельной операцией правил, затем
выбирается явной операцией исключения: изменение справочника само по себе
не переклассифицирует уже созданный автомобиль.

Ответ: ok, vehicleId, vehicleRevision, inputRevision, classification
(`candidate|manual_review|excluded`, vehicleClass или null, ruleVersion,
reasonCodes), requiresDispatcherReassignment. candidate ещё не approved.
Никаких object keys, URL скачивания или содержимого документов в ответе.

## Версии, хранение и старые записи

Предлагаются отдельные технические binding/input revision и неизменяемое
assessment, связанные с точными параметрами, версией правила, evidence
revisions, автором/временем и основанием исключения. Общая vehicles.revision
остаётся для CAS формы. Она меняется также от цвета/фото/одобрения и потому
сама по себе не должна означать новую регистрацию/выбор текущего правила.
Класс в vehicles является серверной проекцией актуального результата.

Существующие0019 snapshots сохраняются без перезаписи/удаления. Их FK на ту же
марку/модель и trigger minYear нельзя ослаблять, чтобы провести исключение.
Новый assessment явно различает фактическую модель и модель-основание,
обычный результат и разрешённое исключение; новый guard проверяет эту связь.
Нельзя выдать старый candidate или свободный caller input за доверенное решение.
Точная добавочная DDL и rollback на populated локальной D1 — этап реализации
после утверждения контракта, не исполненная миграция этого документа.

Записи до внедрения binding не получают выдуманных года, evidence, истории
или версии. Без проверенного года/доверенного результата линия закрыта.
Для перевода старых записей нужен отдельный read-only inventory/план до remote
изменений; новые правила не пересчитывают массово прежние допуски. При явном
изменении марки/модели/года действует текущая версия. Служебная миграция сама
по себе не считается таким изменением. Автоматический seed/активация не разрешены.

## Защита и поведение Admin

Каждый запрос проверяет active staff session, актуальные grants, OWNER MFA.
Mutation повторяет guard в транзакции: отзыв прав/сессии/МFA после чтения,
смена vehicle/evidence/rule revision отменяют запись. Все изменения параметров,
assessment, проекции класса, off_line, idempotency и минимального audit — одной
D1 batch. Ошибка audit или любого шага откатывает всё. Изменение общего правила
атомарно создаёт неизменяемую версию и меняет указатель по CAS; чужие автомобили
не обновляет. Нет клиентской транзакции из последовательных HTTP-запросов.

POST ограничен16KiB, списки условий/evidence —32/8; Idempotency-Key и исходные
revisions обязательны. Повтор того же actor/body/key возвращает прежний итог
только после повторной проверки текущего доступа; другой body с тем же key
конфликтует. 400 — формат,401 — сессия,403 — доступ/MFA,404 — недоступный
объект,409 — revision/version/idempotency,422 — неподтверждённые предпосылки,
429 — существующий throttle. 500 не содержит provider/SQL/raw exception text.
Ответы no-store; курсор привязан к поиску/версии и не несёт PII.

Admin показывает отдельно введённые/проверенные параметры, реальную/сопоставленную
модель, закреплённое правило, условия и причины. Класс только для чтения.
Перед записью — итоговое подтверждение параметров/основания. При неизвестном
результате никаких автоматических POST/refresh/replay: только явный повтор
исходного body/key или чтение состояния. Перед повтором снова grants/MFA.
onStop очищает ввод/evidence/preview/условия/основание и pending операции;
FLAG_SECURE, no SavedState/autofill/disk cache сохраняются. Новый API не
расширяет allowlist OWNER-only STAGING; телефонная активация отдельно.

Audit: actor/target IDs, тип действия, до/после rule/assessment IDs, outcome,
reasonCode, requestId, server time. Не включать VIN, номер, телефон, body,
текст причины, document content/keys/URL, токены. Полное основание находится
только в защищённой истории решения. D5/ретеншн для реальных данных этим
документом не утверждаются.

## Обязательная приёмка реализации после утверждения

Backend: права/OWNER MFA на read/write/replay; unknown/injected fields; год,
Li Auto/BEV/смешанное исполнение; все условия; модель-основание той же марки;
исключение без отдельного права; class только из rule; исправление параметров;
потеря доступа/evidence/current-rule race; audit rollback; idempotency; old
Admin approve bypass; legacy/line/assign/reassign/phase/done SQL guards.
Версии: первое сохранение против конкурентного изменения правила; одна смена
правила не обновляет существующие автомобили; цвет/фото/служебный revision не
подтягивают новое правило; явная смена make/model/year использует текущую.
Populated migration/integrity/FK/rollback и native Worker/D1 обязательны.

Android: строгие DTO с null-классом/годом, текущие grants, confirmations,
readonly class, foreground privacy, смена аккаунта, stale data, потерянный ACK,
явный same-key retry и отсутствие replay; JVM/native/build/lint/security,
actual PNG light/dark/font1.3 и artifact provenance. Existing live/phone/merge/
deploy не считать принятыми по synthetic CI.
