# PUSH-01J — резерв квоты для безопасного отзыва push

Дата: 04.11.2026. Статус: Draft поверх PUSH-01I PR №21; никакого rollout.

## Проблема

Изначальная серверная квота ограничивала все grant-операции общими пятью выдачами на заказ за последние 60 секунд. Пять запросов обычной регистрации могли лишить пассажира возможности сразу запросить revoke-only grant.

## Решение (без новой миграции D1)

- Обычные manage grant: максимум **4** успешные выдачи за скользящие 60 секунд на подтверждённый orderId.
- Revoke-only grant: при исчерпании четырёх обычных выдач можно занять **пятую** позицию, но не больше. Общая квота всех операций — не выше 5 / 60 секунд / orderId.
- Реализовано в существующем атомарном INSERT...SELECT по таблице `passenger_push_grant_events` из ещё не применённой в production миграции 0007. Клиент **не** задаёт purpose: сервер выбирает его только после строгой валидации `operation="revoke"` и проверки read capability.
- Повторные revoke-вызовы также получают 429 после пятой записи. Ни одна функция не обходится без HMAC v2, JWT scope, nonce, D1 owner check.
- В случаях таймаута, 429, истёкшего read-token или отключённой сети приложение не вправе заявлять, что серверная регистрация уже отозвана.

## Истечение пассажирской сессии

- **Никакого неаутентифицированного revoke:** JWT read-token с истёкшим `exp` отклоняется HTTP 403, включая попытку получить revoke-only grant. Это проверяется в изолированном локальном HTTP тесте.
- Серверная функция `maintainPassengerPushData` уже содержит очистку/обезличивание при истечении регистрации и terminal order, **но не вызывается по расписанию и не обеспечивает автоматический отзыв по истёкшему read-token**.
- До production FCM обязателен отдельный этап: ограничить eligibility каждой отправки сроком регистрации и статусом заказа; утвердить срок серверного хранения, интервал плановой очистки/ретраев и fail-closed поведение при недоступности D1. Истечение read-token без установки и проверки этих процедур остаётся блокером.
- При пяти *самих* revoke-запросах окно всё равно блокируется: решение гарантирует только резерв от четырёх manage, а не безусловную доставку revoke при любых перегрузках.

## Тесты

- `tests/passengerPushDeviceRouter.test.mjs` — 4 manage, один revoke, общий потолок, скользящее окно и неверный purpose.
- `tests/passengerPushSecurity.sqlite.py` — настоящий SQLite SQL с теми же параметрами и атомарной проверкой ограничений.
- `tests/passengerPushPhpWorkerD1.integration.mjs` — подписанные PHP HMAC → Worker Router → SQLite grant.
- `tests/passengerPushHttpLoopback.e2e.mjs` — настоящий локальный PHP/cURL → Worker Router → SQLite, отказ по истёкшей read capability, невозможность шестого grant.
- Остальные existing tests (staff/quote/order/FCM) не изменены. Никаких удалённых Cloudflare D1, Workerd deploy, реальных поездок и FCM.

**Не объединять, не деплоить, не изменять конфигурацию Worker/PHP, не устанавливать миграции и не включать Firebase без отдельного разрешения.**
