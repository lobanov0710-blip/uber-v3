# Предложение подготовки схемы автомобильного контура STAGING

25 ноября 2026, Москва. Статус: предложение, не разрешение исполнения.
Документ описывает условный сценарий без действующих автомобильных связок.
Числа/факты из частного отчёта владельца не публикуются. Этот сценарий не
означает пустоту всей D1: OWNER, MFA, сессии, документы, заказы и история
не измеряются тремя автомобильными счётчиками и должны сохраняться.

Из cutoff18 кандидат — 19–25, из cutoff19 — 20–25. Если версия/структура
не совпадает с известным состоянием, выполнение не выбирается автоматически.
Файл20 содержит временный перенос class и DROP COLUMN; файл25 перестраивает
trust-связки. Это нельзя выдавать за DDL без изменений существующих объектов.
Нельзя копировать файлы по одному вручную, повторять применённую миграцию,
пересоздавать D1, очищать таблицы или «исправлять» неизвестную схему наугад.

Кандидат Worker source выше прошёл прежний CI44607369124, но это не утверждение
его установки. Фактическая версия Worker и её совместимость с целевой схемой
должны быть установлены до отдельного выбора rollout. Существующие APP_ENV и
ADMIN_PHONE_TEST_ONLY должны сохранять согласованный OWNER-only STAGING scope;
Driver G1 не возобновляется. Нельзя заменять постоянную подпись Android
одноразовым ключом; подписанная физическая QA-приёмка остаётся отдельным шагом.

## Следующий запрос владельцу: только metadata preflight

Предлагается отдельная read-only процедура, ещё не исполненная и не включённая
в разрешение предыдущего варианта A в части Worker control-plane metadata:

1. Проверить тот же account/config/пинованный UUID. Использовать существующую
   приватную авторизацию владельца; отсутствие прав означает остановку, не
   создание токенов/прав или запрос секретов в чат.
2. Выполнить только уже известный фиксированный metadata SQL: имена d1_migrations,
   типы известных таблиц и PRAGMA table_info. Без SELECT содержимого аккаунтов,
   документов или автомобилей; без агрегатного SELECT и повторного получения
   закрытых чисел. Разрешённый D1 endpoint — POST
   /accounts/{accountId}/d1/database/66474481-a123-47f9-81b4-12af7565ec8d/query;
   тело — ровно metadataSql из закреплённого reader, без произвольного SQL.
3. Прочитать GET /accounts/{accountId}/workers/scripts/uber-v3-staging/deployments.
   Требовать единственную активную версию с 100% трафика; неоднозначность — отказ,
   а не выбор версии за владельца. Другие Workers/accounts не перечислять.
4. Прочитать GET /accounts/{accountId}/workers/scripts/uber-v3-staging/versions/{versionId}
   только для установленного выше versionId. Проверить DB binding UUID и только
   allowlisted scope-параметры APP_ENV=staging, ADMIN_PHONE_TEST_ONLY=true.
   Не запрашивать secrets values и не выводить raw provider response. Ответ
   metadata может содержать другие bindings/vars: они не публикуются и не
   сохраняются в публичную квитанцию. Совпадение UUID в local config само по
   себе не подтверждает deployed binding.
5. Публичный результат — target, source provenance, точный известный cutoff,
   versionId, совпадение DB binding/scope, результат проверки. Без private counts,
   хеша private report, Account ID, иных var values, credentials и raw response.
   Только после согласования этого состава подготовить/проверить отдельный
   ограниченный пакет и точную схему новой квитанции; старый reader не менять
   и не выдавать новый формат как уже утверждённый.

Границы новой проверки: только указанные metadata операции, лимиты времени и
объёма, приватный процесс/ошибки, source/target checks и synthetic tests до
выдачи пакета. Нет writes/deploy/export/import/secrets-reset/доступа к private
метрикам. Согласование metadata preflight не означает согласование миграций.

## Условия будущего отдельного разрешения на обновление

После metadata preflight подготовить окончательный execution packet с точной
версией Worker/schema, полным списком и хешами только недостающих миграций,
совместимостью OWNER API/Android, перечнем остановок и окон изменений.
Перед записью нужно повторно убедиться в актуальности условий целевого контура
и ограничить конкурентные записи по согласованному порядку. Никаких скрытых
административных запросов из этой документации не выполняется.

Восстановление и сохранность данных должны иметь конкретный проверенный порядок
до будущей записи. Старый Worker нельзя считать универсальным rollback после
изменения схемы. Full SQLite export, backup и restore не входят в вариант A;
их механизм, доступ, закрытое хранение и проверка восстановления согласуются
отдельно. До этого обновление не является execution-ready.

После отдельно разрешённого этапа проверять FK/quick_check, сохранность OWNER/MFA,
существующих записей/истории/pins, schema contracts и OWNER-only поведение.
Отрицательные тесты: Dispatcher (включая ошибочные grants), Driver, без MFA,
неполные/неподходящие параметры, BEV и запрещённые кузова. Тестовые аккаунты и
записи создаются только в явно разрешённом изолированном контуре, не попутно.

Установка schema не равна загрузке каталога или активации классификатора.
Seed/backfill/изменение pins/автоматический допуск не включены. Прежние правила
новых регистраций и критического редактирования сохраняются; исключения —
только OWNER/MFA, класс вычисляет система. При остановке поездки замена водителя
только вручную диспетчером. G1 paused, D4–D7 pending; 111 range followups не закрыты.
